# Frontend

Next.js 16 App Router + React 19 + TypeScript. Plain CSS in `src/app/styles.css` (no UI library).

## Layout
- `src/app/[market]/…` SSR storefront (server components): home grid, product page, cart, order confirmation. Market code in the URL (`/uk`, `/us`, `/ca`); unknown market → 404.
- `src/app/admin/…` admin. `layout.tsx` is a client component: login gate (`/api/auth/me`), dark sidebar, search (⌘K), orders badge. Pages are thin wrappers around `src/components/admin/*`.
- `src/components/admin/` client components: `Home`, `Dashboard` (Analytics), `ProductList`/`ProductEditor`/`PrintLabels`/`CodePreview`, `Orders`/`OrderDetail`/`DraftEditor`/`Label`, `Customers`, `Markets`, `Pages`/`Preferences`/`Menus` (Online Store), settings screens (`Settings` exports `ShipFrom`/`EmailSettings`/`Appearance`/`PasswordCard`; plus `AccountSettings`, `Users`, `Roles`, `Locations`, `Policies`, `Payments`), `StoreSwitcher`, `NoAccess`, `validation.tsx`, `hooks.tsx` (`useApi`, `Badge`, `TagList`), `nav.ts` (sidebar links, settings links, ⌘K actions, each with the permission it needs).
- `src/components/store/` cart context (per-market localStorage), `AddToCart`, `CartPage` (quote + Stripe checkout), `ClearCart`.
- `src/lib/api.ts` `api()` for `/api/admin/*`, `auth()` for `/api/auth/*`, money helpers. `src/lib/store.ts` server-side fetch to the backend for storefront SSR (revalidate 60s).
- `next.config.mjs` rewrites `/api/*` to `BACKEND_URL` (default `http://localhost:4000`).

## Conventions
- Storefront data is fetched in server components via `src/lib/store.ts`. Interactive bits (cart, add-to-cart) are small client components. Add `generateMetadata` to new storefront pages.
- Admin components start with `"use client"`. A 401 from any admin call fires `admin:unauthorized` and the layout returns to the login screen.
- Storefront look: warm cream theme, classes prefixed `sf-`/`pcard`/`pdp`/`hero`. Generic class names (`card`, `hero`) collide with other rules, so use specific names (the product placeholder art uses `art-ph sm|lg`). `ProductArt` is the gradient fallback when a product has no image.
- Admin styles are scoped under `.admin`, storefront under `.store`. Don't add unscoped global rules.
- Prices shown to users come from the server (`/api/store/quote`); the client sends only variant ids and quantities.
- Deep links: `/admin/products?new=1`, `/admin/markets?new=1`, `/admin/orders?status=open`.
- Don't use `useSearchParams` in pages without a Suspense boundary (static prerender fails); read `location.search` in an effect instead.

## Orders, drafts, labels
- `/admin/orders` list with tabs (incl. Drafts) → `/admin/orders/[id]` (`OrderDetail`: totals, payment link / mark paid for drafts, tracking + fulfil for orders) → `/admin/orders/[id]/label` (`Label`: 4x6 label, `?type=slip` packing slip; print CSS hides the sidebar). `/admin/orders/new` and `/[id]/edit` use `DraftEditor` (live totals from `/api/admin/drafts/quote`). Carrier list + tracking URL templates in `lib/carriers.ts`.
- Provinces: product form shows a province picker per market with regions; cart page has a province select and takes the tax label from the quote response.

## Product images
- Admin: `ImageManager` inside the product form. New files wait as "pending" until the product is saved (then `uploadImage` posts the raw file body to `/api/admin/products/:id/images`); existing images reorder/alt/delete immediately. Storefront: `<img>` thumbs on cards, `Gallery` on the product page, `ProductArt` gradient when a product has no image. `/uploads/*` is proxied to the API.
- Controls are styled once at the end of `styles.css` (custom select chevron, one button height, mobile drawer). Don't restyle `select`/`button` per component.

- Storefront data goes through `lib/store.ts`, which fills missing fields (`images`, `regions`, ...) because Next can serve a cached API response from an older shape; pages may rely on those fields. Icons next to labels (`components/Icons.tsx`: Plus, ArrowLeft, ArrowRight, External) are SVGs so buttons/links can space them with `gap`; don't type `+`/`→` glyphs into labels.

## Rich text and HTML code
Every long-text field that is HTML (product description, pages, policies) uses `RichTextEditor`, which has a `</> HTML` button to edit the source. Pasted code goes through `lib/cleanHtml.ts` (DOMParser allow-list, mirrors the server) before it is shown, so `onerror=`/`<script>` can never run inside the admin; the real gate is `sanitizeDescription` in `backend/src/html.ts` on every save. Allowed: formatting, links, lists, headings h2-h4, tables, images (src must be http(s) or a `/` path), `pre`/`code`, and iframes ONLY from youtube.com / youtube-nocookie.com / player.vimeo.com. Everything else (scripts, styles, classes, inline handlers, other iframes, forms) is removed, so keep the client and server allow-lists in sync. Plain textareas (notes, meta descriptions, address fields) stay plain text on purpose. Storefront styling for the richer tags is under `.sf .desc`.

## Variant editor
Variants are cards (`.vcard`), not a table, so nothing scrolls sideways: per-market price and compare-at (the crossed-out "was" price, must be above the price, display only), quantity, weight, then SKU and barcode side by side with Generate, plus "Preview barcode and QR". Don't go back to a wide table.

## Product pages
- List: `ProductList.tsx` (same pattern as Customers: views Active/Draft/Archived, stock chips, column picker via shared `ColumnsMenu`, bulk activate/draft/archive/delete, CSV export) against `GET /products/list`. Editor: `ProductEditor.tsx` (two columns like Shopify). Adding options (Size, Color) rebuilds variants with `syncVariants`: existing combinations keep their data, refinements inherit (first child takes the old variant, others copy prices only because SKUs are unique), so never replace it with a plain regenerate. Description is edited in `RichTextEditor` (execCommand) and sanitized by the API on save. Toggles use `Switch`.
- "New customer" is a page rendered in the main panel in place of the page that opened it (`NewCustomerSheet`); callers `return` it early after all hooks so their state (e.g. the draft order being built) survives.

## Field styles
`Settings > Appearance` lets staff pick one of five input looks (default: "filled", no border; storage key `fieldStyle.v2`) (`lib/fieldStyle.ts`, generated `app/fields.css`, attribute `data-fields` on `<html>`, set early by an inline script in `app/layout.tsx`). They are `!important` override layers on top of the base field styles, so a new kind of input must be added to the selector list in `fields.css` to follow the choice. The filled style gives fields placed straight on the gray page (`.sidesec`, `.pagehead`) a darker fill so they stay visible; put new page-level fields inside one of those or inside a white `.card`.

## Form validation
Every input shows its own error under it. Pure validators live in `lib/validators.ts` (required, email, phone, money, int, decimal, postcode by country). A form builds an `errors` record from its state each render and passes it to `useValidation` (`components/admin/validation.tsx`): spread `val.props(key)` on the control (aria-invalid, blur = touched), render `<FieldError k msg={val.err(key)} />` below it, and call `val.submit()` in Save (shows all errors, focuses the first invalid field, returns false when invalid, so no request is sent). Server conflicts (duplicate SKU/email/handle, API 409) are mapped back onto the field. Errors from blur wait until the pointer is released so a layout shift cannot swallow a button click. Invalid styling is at the end of `fields.css` and covers all five field styles. Used in ProductEditor, NewCustomerSheet, AddressModal, DraftEditor, Settings, Markets, admin login and storefront checkout (`CartPage`). Don't disable Save buttons for invalid input; let the user click and see why.

## SKU, barcode, QR
`lib/codes.ts`: `makeSku` (UV-NAME-OPTION, de-duplicated), `makeEan13` (prefix 2 = GS1 internal range, valid check digit), `barcodeError` (numeric 8/12/13/14-digit barcodes must have a correct GS1 check digit; other text is allowed), `ean13Svg` (draws EAN-13/UPC-A). ProductEditor has Generate (SKU, barcode), "Generate missing" (all variants) and Preview (`CodePreview`: barcode SVG + QR via the `qrcode` package, download, print label). Generation checks the other variants and `POST /products/codes/taken` (other products' SKUs/barcodes) so it never makes a duplicate; SKU is unique in the DB (case-insensitive), barcode is not but the form warns on duplicates.

## QR codes open the product page
A QR code holds a URL, not the bare SKU (phones would just google it): `productQrUrl(base, code)` = `<base>/p/<SKU or barcode>`. `app/p/[code]/page.tsx` calls `GET /api/store/lookup/:code` (active products only, SKU or barcode, prefers `?market=`) and redirects to `/<market>/products/<handle>?variant=<id>`, where `AddToCart` highlights the scanned variant. `base` comes from `useQrBase()`: Online Store → Preferences → "Public store URL" (`publicUrl`), else `location.origin`; if that is localhost the preview and label page warn that phones can't open it. EAN-13 barcodes are for scanner guns/POS: a phone camera reads them as a number and searches the web, so use the QR on labels for customers. Draft/archived products are not exposed by the scan.

## Print labels
`/admin/products/labels` (`PrintLabels.tsx`, entry: Products list "Print labels", preselects selected products via `?ids=`): pick variants (size/colour shown from `variant.options`), copies per variant (or stock qty), label stock (50x25 / 70x40 roll, A4 21-up / 65-up sheets with "already used" slots), fields (name, variant, SKU, EAN-13 barcode, QR of SKU, price per market). Prints through `window.print()`; `@page` size is injected per stock and `.noprint` hides the controls. Each variant has its own SKU and barcode (SKU column + More in the editor).

## Staff, roles, settings area
`/admin/settings/*` swaps the main sidebar for a Settings sidebar (`settingsLinks` in `nav.ts`, "← Settings" goes back): General (ship-from), Users, Roles and permissions, Notifications (email), Appearance, My account (name + password). `/api/auth/me` returns `{role, owner, permissions[]}`; `lib/perms.tsx` `useCan().can("orders.view")` (manage includes view; owners can do everything) and `ROUTE_PERMS` (path prefix → permission). The layout hides nav links and search results the user can't use and renders `NoAccess` for blocked routes. This is only convenience: the API enforces everything (`guard()` per router in `backend/src/index.ts`). New admin screen = add its prefix to `ROUTE_PERMS`, its link to `nav.ts` with `perm`, and a `guard` for its router.

## Locations, policies, store switcher
Settings → Locations (`Locations.tsx`, table `Location`): the default location is the sender on labels/packing slips; `GET/PUT /settings/ship-from` now read/write it (`shipFromAddress()`), General's address card edits the default location, and `ensureDefaultLocation()` turns a legacy ship-from setting into the first location. First location is always default; the default can't be deleted or deactivated. Stock is still per product, not per location. Settings → Policies (`Policies.tsx`, table `Policy`, 7 fixed keys in `routes/policies.ts`): empty = not published, published ones show in the storefront footer and at `/<market>/policies/<key>` (fetched `no-store`, same stale-200 reason as pages); starter templates have [brackets] to fill in. Under `/admin/settings` the same main sidebar (`.side.main.collapsed`, labels are `.navlbl`, don't call anything `.lbl`: that is the print-label preview) shrinks to an icon rail and the settings menu (`.side.setpanel`) slides in beside it. It is pure CSS transitions on the `.shell` grid columns, labels and store button, so it animates both ways and is skipped under reduced motion; on phones the main nav is hidden in settings and the settings menu is the drawer. The store menu is rendered through a portal into `.admin` with fixed positioning (the sidebar's overflow would clip it). `StoreSwitcher` (bottom of the sidebar; the signed-in user and Log out live in its menu, there is no separate user block) lists the current store, View online store, and a Create store explainer: there is no multi-store support, a second store is a second deployment.

## Online Store
Sidebar group (Shopify style) with **Pages** and **Preferences** (`app/admin/online-store/*`, components `Pages`, `Preferences`, `Menus`). Pages = `Page` table (title, unique handle, sanitized rich-text content, visible, SEO), CRUD under `/api/admin/online-store/pages`, shown at `/<market>/pages/<handle>` (hidden = 404). Preferences = one JSON blob in `Setting` key `onlineStore` (store name, tagline, announcement bar, home title/description, header and footer menus; menu links are `/pages/about` style paths relative to the market, or full https/mailto). The storefront layout reads it through `getSite()` (falls back to defaults if the API fails). `getPage` is fetched with `no-store` on purpose: Next never replaces a cached 200 with a later 404, so a hidden/deleted page would stay online. Not built: Themes, Blog posts.

## Collections, blog, gift cards, import, postage
- `Collections.tsx` (`/admin/collections`): list + editor, manual (add-products modal, reorder) or automated (rule builder with a debounced live preview from `POST /collections/preview`). Storefront: `/[market]/collections` and `/collections/[handle]` use the shared `components/store/ProductGrid.tsx`; the home page shows collection chips.
- `BlogPosts.tsx` (`/admin/online-store/blog`): drafts, publish, schedule (datetime-local), cover upload to `/api/admin/blog/images`. Storefront `/[market]/blog` and `/blog/[handle]` fetch `no-store` (like pages) so unpublishing 404s straight away.
- `GiftCards.tsx` (`/admin/gift-cards`): issue (currency chosen per card), detail modal with ledger, adjust, email, disable. Product editor has a "Gift card" switch (forces physical/tax/stock off). Storefront `CartPage` has a gift card box: the server re-prices on every quote (`giftCardApplied`, `amountDue`); when `amountDue` is 0 the button reads "Place order" and checkout skips Stripe.
- `ShopifyImport.tsx` (`/admin/products/import`): choose CSV (sent as `text/csv`, not through `api()`), map each market to a price column, import in batches of 10 handles with progress and a per-product result table. Menus quick-add offers Blog, All collections, each collection and pages.
- `ShippingLabel.tsx` (card on the order page): parcel size -> rates -> explicit "Buy label" with a confirm naming the price; void; shows "not switched on" until `SHIPPO_API_KEY` is set. The label URL is only linked when it is https.
- File pickers use a visible `<button>` that clicks a hidden `<input type=file>` (`label.btn-link` renders badly). Radios are styled in `styles.css` next to checkboxes.

## Dropdowns
Never use a native `<select>` (the browser draws its list and it can't be styled). Use `components/Select.tsx`: same `<option>` children and `value` / `onChange={(e) => e.target.value}` as a select, but a custom trigger (`.selectbtn`, covered by every field theme in `fields.css`) and a portal list (`.selectpop`): check mark on the selected row, arrow/Home/End/Enter/Escape and type-ahead, a search box when there are more than 8 options, flips upward near the bottom of the screen, storefront colours when inside `.store`. The trigger carries `iconbtn` only to skip button hover effects, so its size is forced in `styles.css`.

## Customers list
`components/admin/Customers.tsx` mirrors Shopify's list: search, filter chips (stand-in for the AI segment bar), sort + column picker (`ColumnsMenu`: eye toggles, drag or ↑/↓ to reorder; view saved in localStorage key `customers.view.v1`), row selection, 50-per-page paging via `GET /api/admin/customers?q&filter&sort&dir&limit&offset` → `{items,total}`. Export uses `download()` (authenticated blob). Import (`ImportCustomers`, `lib/csv.ts`) reads Shopify's customer CSV or our own export and posts 500-row chunks to `/customers/import`. To add a column, add one entry to `COLS` (and the field to `customerRows` in the backend if it isn't there yet).
- Global button/field rules use `:where(...)` so component styles (icon buttons, chips, list rows) can override them. Don't re-add `:not()` chains with higher specificity.

## Motion and overlays
- `Modal` (centered dialogs) and `Drawer` (right panel for long forms) are the only overlay components; both close on Escape, `dismissOnScrim={false}` protects typed data. Nested dialogs sit above (`.modal-scrim` z-index > `.drawer-scrim`).
- All field/button motion lives in the "motion" block at the end of `styles.css` (hover border, blue focus ring + label, press/lift on buttons, dropdown/dialog/drawer entrances). It is disabled under `prefers-reduced-motion`. New form controls inherit it automatically; don't add per-component transitions.

## Verifying UI work
`npm -w frontend run typecheck` and `npx next build` (from `frontend/`). Then look at it for real: Playwright (`playwright-core` + the Chrome binary) logs in at `/admin`, drives the flow, asserts, and screenshots (keep scripts and shots in the scratchpad, not the repo). Gotchas found the hard way: the storefront caches API fetches for 15s with stale-while-revalidate, so load a page twice after an admin change; `no-store` is used for pages/policies because Next never replaces a cached 200 with a later 404; wait for hydration/animation before asserting or screenshotting (popups fade in); a blur-triggered error must not move a button during a click (handled in `validation.tsx`). Check phone width (390px) for horizontal overflow on every new screen. Class names are global per scope: don't reuse short names (`.lbl` is the print-label preview, the sidebar text is `.navlbl`). Remove any test data you created.

## SEO and security headers
- `next.config.mjs` sets headers on every route: CSP (script-src needs `'unsafe-inline'` for Next's bootstrap; `'unsafe-eval'` and `ws:` only in dev), HSTS (production only), nosniff, X-Frame-Options DENY, Referrer-Policy, Permissions-Policy (camera/mic/geo off; nothing in the app uses them), COOP same-origin. `/admin/*` and `/api/*` get `X-Robots-Tag: noindex`. `poweredByHeader` is off. Forms may post only to self or `checkout.stripe.com`; if you add a third-party script, image host (`img-src` allows https) or iframe, extend the CSP there.
- `NEXT_DIST_DIR=.next-x npx next build|dev -p <port>` runs a second build/server beside the main one (gitignored `.next-*`).
- `lib/seo.ts`: `siteOrigin()` (Online Store `publicUrl` preference, else `NEXT_PUBLIC_SITE_URL`, else `STOREFRONT_URL`, else localhost:5173), `marketAlternates()` (canonical + hreflang `en-GB/en-US/en-CA` + `x-default`), `priceStr()`. `components/store/JsonLd.tsx` renders JSON-LD with `<` escaped.
- Pages: product (Product + Offer per variant + BreadcrumbList, hreflang only between markets that sell it), collection (CollectionPage + ItemList + BreadcrumbList), home (Organization + WebSite), blog post (BlogPosting + BreadcrumbList). Blog, CMS pages and policies read the same in every market, so their canonical is the default (first) market. Titles/descriptions use the SEO fields, falling back to content. Cart, order and `/p/*` are `noindex`. `app/not-found.tsx` is the 404 (noindex).
- `app/sitemap.ts` and `app/robots.ts` are built on request from the public API (hreflang alternates for multi-market pages; CMS pages come from the header/footer menu links because the API has no page list). One `<h1>` per page; product images carry `alt`, width/height, and lazy loading except the gallery main image.
- Optional `sku`/`barcode` on store variants add `sku`/`gtin` to the Product JSON-LD once the API returns them (it does not yet).

## Marketing, apps, security and checkout admin screens
- `/admin/marketing` (`Marketing.tsx`, perm `integrations.manage`): Google XML / Meta CSV feed URLs per market (copy boxes), abandoned-checkout email toggle + delay, stats and the list of unpaid checkouts with a per-row "Send reminder" (only customers who ticked the cart-reminder box).
- `/admin/settings/apps` (`Apps.tsx`, `integrations.manage`): API keys (role dropdown hides Owner and roles that manage staff/integrations; secret shown once in a modal) and outbound webhooks (events from the API, signing secret shown once, "Send test", last deliveries) plus signature-verification notes. This is the replacement for Shopify apps.
- `/admin/settings/security` (`Security.tsx`, any staff): own two-factor sign-in (start, QR via `qrcode`, confirm code; disabling needs password + code) and the security log (only with `users.manage`). Users modal has "Reset two-factor".
- `/admin/settings/checkout` (`CheckoutSettings.tsx`, `settings.manage`): automatic tax (Stripe Tax) toggle, high-value first-order threshold, fraud screening explainer.
- Login (`app/admin/layout.tsx`): a 401 containing "6-digit" or "code is not right" reveals the code field (`autocomplete="one-time-code"`) and resubmits with `code`.
- Orders: `Order.riskLevel/riskNote` drive a banner on `OrderDetail` (medium amber, high red, confirm before fulfilling a high-risk order) and a "Review" / "High risk" badge in the orders list.
- Shared: `CopyBox.tsx` (read-only text + Copy). The role `Select` is the custom dropdown (not a native `<select>`), so UI tests click the trigger then `[role=option]`.
